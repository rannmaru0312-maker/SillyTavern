# AI共同開発の運用

## 正式な引き継ぎ元
GitHub Issue → 専用ブランチ → ドラフトPR → コミットSHAに対応したChecks。
Work、Copilot、みやは直接会話を自動同期しない。前担当のチャットだけを根拠に完了としない。
本規約の隔離checkoutは、既存規約の開発ディレクトリ指定をクラウドWorkにも適用するための補足である。

## タスク開始と引き継ぎ
1. MIYA AI共同開発のIssueフォームで目的・完了条件・対象範囲を記入する。
2. 担当AIを一人決め、開始SHAと作業ブランチをIssueに記載する。
3. miya-ai-devから専用ブランチを作成する。既存PR #2の変更を別PRへ無断で混ぜない。
4. PR本文に Related issue: #番号、変更理由、テストコマンド・結果・SHA、未確認事項を記す。baseはmiya-ai-dev、draft=true。
5. 引き継ぎ時はIssueに完了作業、最新SHA、PRリンク、CIリンク、残作業、次の担当を追記する。
6. 新担当はremoteの最新SHAと差分を再確認する。過去の成功したCIを新コミットの結果として扱わない。

## Copilotの初回設定（手動ゲート）
GitHubのAssign to Copilot画面で対象リポジトリとbase=miya-ai-devを明示選択する。
選択できない場合は割り当てない。デフォルトブランチには依存しない。
初回は小さな架空データのタスクを手動で割り当て、生成PRのbaseとdraft状態を実際に確認し、証拠リンクをIssueに記録する。
Copilotの利用契約・組織設定によって利用可否は異なる。Actions実行に承認が求められる場合は人が内容を確認する。
この設定には自動Issue割り当て、マージ、デプロイを含めない。初回確認だけで自動割り当てを有効にせず、別途設計・承認する。
公式手順: https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github

## CIの範囲と限界
MIYA AI Development Checkはmiya-ai-dev宛PRで実行。読み取り専用権限、checkout認証非保持、依存インストールのscript無効化、変更JSのESLint、全Jestを直列実行する。
安全確認は保護データパス、代表的な秘密鍵・GitHubトークン形式、差分の空白エラーを検出する。個人情報全般を自動で検出する保証はない。
CIと規約は権限の境界ではない。管理者は開発ベースに必要なチェックとレビューを設定し、releaseへの書き込みを制限すること。本作業ではrelease設定は変更しない。
既存の公開用workflowは変更しない。新規CIは公開用workflowを呼び出さない。

## WorkのPRイベント連動
対応イベント: PR作成・更新(synchronize)・再レビュー可能化等。コミット更新を有効にしてrepositoryを指定し、実行時にbase=miya-ai-devだけを対象にする。
処理は差分レビュー、Issue/PR履歴確認、最新SHAのActions状態確認、日本語のチャット報告。コード変更・コメント投稿・マージ・デプロイは自動化しない。
Actions完了イベントそのものは今回確認したPRイベントの対象外。更新直後のCIが実行中なら「実行中」と報告する。完了後の確認は手動で依頼する。
既存タスクを1件停止して枠を確保した後、WorkからPRイベント連動タスクの登録成功が報告された。PRイベントを受けた初回実行と通知の動作確認は未完了。既存タスクを追加で停止・削除しない。

## 導入順
この変更を専用ブランチからmiya-ai-dev宛のドラフトPRにする。レビュー後のマージは人が判断する（AIはマージ禁止）。
指示ファイルが開発ベースに入るまでは新規タスクに自動適用されない。Issueフォームが表示されない場合はこの文書の項目を通常Issueに貼る。releaseへテンプレートを入れることはしない。
